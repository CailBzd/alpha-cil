## security

Fair — the RLS/SECURITY DEFINER model is mostly careful and shows real evidence of prior hardening (e.g. `0018_acces_carnet_scope_interventions.sql` fixing a cross-tenant leak, the `0e5e193` persona-guard fix, deliberate `revoke ... from public` on the cron RPC), but one SECURITY DEFINER function still leaks another owner's email to any signed-up account, and the cron secret check has a classic "undefined equals undefined" bypass if the env var is ever unset.

| Sev | Category | Location | Issue | Suggested fix | Effort |

| 🔴 | security | `supabase/migrations/0022_dpe_detail_et_infos_logement.sql:170-179` (also the earlier version at `supabase/migrations/0008_rattachement_logement.sql:66-74`) | `match_or_create_logement(p_adresse, p_contact_email, ...)` is `grant execute ... to authenticated` (see `:210-212`) with no caller-role check inside the function body. When `p_adresse` matches an already-claimed logement, it returns `v_notify_email` (the real owner's email, read via `auth.users`). Any signed-up account — including a self-serve propriétaire created through `apps/web/app/api/proprietaire/signup/route.ts` with zero verification — can call this RPC directly via PostgREST (`{SUPABASE_URL}/rest/v1/rpc/match_or_create_logement`, bypassing the Next.js route and its artisan-only UI) and harvest the owner's email for any guessed/known address. This is the same class of cross-tenant leak fixed in `0018_acces_carnet_scope_interventions.sql`, just not caught for this function. | Add a caller check inside the function (`if not exists (select 1 from public.artisans where id = auth.uid()) then return query select ... end if;`, mirroring the pattern already used in `get_rendez_vous_owner_email` at `supabase/migrations/0030_rendez_vous.sql:196-205`), or stop returning `notify_email` from the RPC entirely and send the "logement already claimed" notification from a separate, narrowly-scoped path. | M |
| 🟡 | security | `apps/web/app/api/cron/rappels-entretien/route.ts:31` | `if (authorization !== \`Bearer ${process.env.CRON_SECRET}\`)` — if `CRON_SECRET` is ever unset in a deployment (misconfigured preview env, accidental omission), `process.env.CRON_SECRET` is `undefined` and the template literal becomes the literal string `"Bearer undefined"`. Anyone who sends `Authorization: Bearer undefined` then passes the gate and can trigger the cron (service-role DB writes + mass email send to every owner due for a reminder). Contrast with `packages/db/client.ts:15-21`'s `requireEnv`, which fails closed for the other secrets. | Fail closed: `if (!process.env.CRON_SECRET || authorization !== \`Bearer ${process.env.CRON_SECRET}\`)`. | S |
| 🟡 | security | `supabase/migrations/0007_artisans_update_self.sql:7-11` (grant at same file, acknowledged in `supabase/migrations/0032_artisan_profil_societe.sql:12` comment: "siret itself stays read-only in the UI (not DB-enforced...)") | `artisans_update_self` allows an artisan to update every column on their own row via `using/with check (auth.uid() = id)`, including `siret` — the UI (`SocieteForm.tsx`) never sends it, but nothing stops a direct `supabase.from("artisans").update({siret: ...})` call. Since `interventions_select_owner`/RGE verification and the owner-facing "who did this work" trust story (`artisan_siret` denormalized per intervention) rest on the SIRET being the one verified at signup, an artisan can post-hoc rewrite it to any other 14-digit number, undermining that verification for future interventions. | Restrict the grant to column-level: `grant update (denomination, adresse, telephone, corps_metier) on public.artisans to authenticated`, dropping blanket `update` so `siret` (and `corps_metier`'s trust anchor) can only change through a re-verification path. | S |
| 🟢 | security | `supabase/migrations/0025_devis_projets.sql:77-86` | `devis_insert_owner`'s `with check` only verifies the target `projet_id` belongs to the caller's own logement — it never checks that `contact_id` also belongs to that same propriétaire (contrast with the fix pattern in `0018_acces_carnet_scope_interventions.sql:13-28`, which added exactly this kind of second check for grant/intervention pairing). A caller who somehow learns another owner's `contact_id` UUID could attach it to their own devis row. Low real impact today since `contacts_select_owner` RLS still blocks reading that contact's actual data through any embed, but it's the same missing-cross-table-check shape as a previously real bug. | Add `and exists (select 1 from public.contacts c where c.id = devis.contact_id and c.proprietaire_id = auth.uid())` to the insert (and update) check. | S |
