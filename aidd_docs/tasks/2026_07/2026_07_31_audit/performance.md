## performance

Fair — the app's data-fetching architecture (Server Components, batched queries, Map-based joins instead of N+1) is solid and heavy libs are already kept out of the shared bundle, but all 33 migrations contain zero `CREATE INDEX` statements, so every RLS-filtered foreign key (logement_id, artisan_id, projet_id, contact_id, agence_id) will force sequential scans as soon as tables grow past a trivial size.

| Sev | Category | Location | Issue | Suggested fix | Effort |
| --- | --- | --- | --- | --- | --- |
| 🟡 | performance | `supabase/migrations/*.sql` (all 33 files) | No `CREATE INDEX` anywhere in the schema. Every RLS policy and every app query filters by a foreign key that has no index: `interventions.logement_id`/`artisan_id` (`supabase/migrations/0003_interventions.sql:11`, queried at `apps/web/app/(owner)/proprietaire/espace/finances/page.tsx:35`, `apps/web/app/(owner)/proprietaire/espace/calendrier/page.tsx:28`, `apps/web/app/(owner)/proprietaire/espace/page.tsx:57`), `rappels.logement_id` (`supabase/migrations/0024_gestion_rappels.sql:10`), `rendez_vous.logement_id` (`supabase/migrations/0030_rendez_vous.sql:14`), `projets.logement_id` and `devis.projet_id` (`supabase/migrations/0025_devis_projets.sql:11,21`), `contacts.proprietaire_id` (`supabase/migrations/0023_carnet_contacts.sql:10`), `logement_access_grants.logement_id`/`agence_id` (`supabase/migrations/0011_acces_carnet.sql:7`, `supabase/migrations/0027_logement_access_grants_agence_claim.sql:6`). At near-zero traffic this is invisible, but it will bite the first time any single logement accumulates a normal multi-year intervention/rendez-vous history, and it compounds on every RLS check (`supabase/migrations/0010_interventions_select_owner.sql:14-21`, `supabase/migrations/0025_devis_projets.sql:66-75`, `supabase/migrations/0028_logements_interventions_select_agence.sql:17-34`). | Add one migration with `create index on <table> (<fk_column>)` for each FK listed above (plus `logement_access_grant_interventions.intervention_id` for the reverse lookup direction). | S |
| 🟡 | performance | `packages/intervention/src/sirene.ts:36`, `packages/intervention/src/ademe.ts:22`, `packages/logement/src/dpe.ts:37` | `verifySiret`, `verifyRge`, and `lookupDpe` all call bare `fetch(url)` against government APIs with no `AbortSignal`/timeout. If `recherche-entreprises.api.gouv.fr` or `data.ademe.fr` stalls, the request hangs until the platform's own function timeout instead of failing fast into the existing catch-and-degrade path. | Add `AbortSignal.timeout(5000)` (or similar) to each `fetch` call. | S |
| 🟡 | performance | `apps/web/app/api/artisan/interventions/route.ts:84,123` | `lookupDpe(adresseLogement)` and `verifyRge(artisan.siret, dateIntervention)` are independent (one depends on the address, the other on the artisan's SIRET) but are awaited sequentially, doubling the worst-case latency of an already slow, external-API-dependent submission path. | Run both with `Promise.all([...])` before the calls that need their results. | S |

Not a problem yet at near-zero traffic/short history, but there's no pagination to fall back on once a logement has years of data. | Add `.range()`/`.limit()` plus a "load more"/pager once histories grow past ~1-2 screens; not urgent pre-launch. | M |
| 🟢 | performance | `apps/web/app/(owner)/proprietaire/espace/LogementMap.tsx:29` | Client component re-geocodes the logement's address via `api-adresse.data.gouv.fr` on every mount of the owner home page (address rarely changes), adding an external round-trip and a loading flash on every visit instead of caching lat/lon once. | Persist geocoded lat/lon on the `logements` row when the address is set/edited (already the case in `AdresseForm`/`create_logement_from_adresse`), and only re-geocode client-side as a fallback when they're null. | S |

Next's route-based code splitting already keeps it out of the shared bundle (only loaded when visiting `/finances`), so this is a minor missed optimization, not real bloat. | Wrap `FinancesCharts` in `next/dynamic(..., { ssr: false })` for a slightly smaller/faster initial paint of that one route. | S |

Positives worth noting: nearly every list page is a Server Component doing a small number of batched Supabase queries joined in-memory via `Map` (e.g. `apps/web/app/(owner)/proprietaire/espace/projets/page.tsx:33-43`, `.../projets/[projetId]/page.tsx:49-54`, `.../(agence)/agence/espace/page.tsx:38-48`) rather than N+1 per-row queries; `@react-pdf/renderer` is only ever imported server-side (`apps/web/app/api/proprietaire/export/pdf/route.ts:2`), never reaching the client bundle; and `leaflet`/`react-leaflet` are already properly isolated behind `next/dynamic(..., { ssr: false })` (`apps/web/app/(owner)/proprietaire/espace/LogementMapClient.tsx:5-12`).
